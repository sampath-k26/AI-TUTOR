## Findings

1. **✅ FIXED — Quiz answer key was leaked in the API response before the user answers (Medium/High).** `POST /projects/:id/quizzes/:quizId/next-question` was returning the full DB row including `answerKey` — `{"correctIndex": 1}` for MCQ, `{"expectedKeyPoints": [...]}` for open-ended — directly in the JSON, before any answer was submitted. The frontend UI never rendered this, but anyone opening DevTools' Network tab, or calling the API directly, could trivially see the correct answer ahead of time. **Fix**: `assessment/router.ts` now strips `answerKey` at the HTTP boundary (destructure-and-omit before `res.json`) rather than in the service layer, since `scripts/runEval.ts` legitimately needs the full row internally to drive its automated eval cases. Re-verified live: the response no longer contains `answerKey`, and grading still works correctly (commit `e2adcd2`).

2. **✅ FIXED — Non-PDF upload returned a generic 500 instead of a 400 (Low).** `multer`'s `fileFilter` (`materials/router.ts`) was rejecting a non-PDF by throwing, which the global error handler (`main.ts`, which treats every forwarded error as an opaque 500) couldn't distinguish from a genuine server fault. **Fix**: `fileFilter` now calls `cb(null, false)` instead of throwing, so a rejected file simply leaves `req.file` unset and falls through to the route's existing 400 check. Re-verified live: `{"error":"A PDF file is required (field name: file, PDF only)"}` / 400 (commit `e2adcd2`).

3. **Tutor errors surface a raw technical string to the end user (Low, UX, not fixed).** When `/tutor/messages` fails (e.g. this quota outage), `TutorTab.tsx` renders the caught error's message verbatim: "Request to /projects/.../tutor/messages failed with 500" — functional and not a crash, but not the kind of message a non-technical user should see. Left as a follow-up since it wasn't part of the requested fix scope.

4. **Gemini free-tier daily quota is a real, easy-to-hit constraint (Info, already documented in `CLAUDE.md`).** One material upload plus a handful of Tutor/quiz calls was enough to exhaust the 20/day cap on `gemini-3.6-flash` in a single session. Not an app bug, but worth planning the demo recording (`docs/13-DEMO-VIDEO-SCRIPT.md`) around fresh quota.

5. **Local-dev gotcha (not a shipped-code defect): restarting the API server does not restart the background worker.** `apps/api` runs two independent processes — `npm run dev` (the Express API) and `npm run worker` (the pg-boss job processor) — by design, so the API stays responsive even if job processing backs up (see `runWorker.ts`'s own comment). During this test pass, two stale worker processes from earlier in the session kept running with an outdated `GEMINI_API_KEY` long after `.env` was updated and the API server restarted, causing every background-job-dependent feature (recommendation generation) to keep failing with a stale key's exhausted quota while synchronous features (Tutor, quiz generation, both handled directly in the API process) correctly picked up each new key. Found via `ps aux | grep runWorker`, fixed by killing the stale processes and starting one fresh worker. **Takeaway for future sessions: after any change to `GEMINI_API_KEY` (or any env var the worker reads), restart both `npm run dev` and `npm run worker`, not just one.**
